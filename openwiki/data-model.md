# Data Model

Prisma 6 + PostgreSQL (Neon). Schema lives in `packages/db/prisma/schema.prisma`; the client is generated to `packages/db/generated/client` (custom output path, outside `node_modules`, to fix pnpm monorepo resolution — it is generated by `postinstall`, never committed).

## Shape

**18 models**, **9 enums**. All tables map to snake_case plural names (`@@map`); all PKs are cuid strings.

### Enums

`ClubKind` (11), `ProductCondition` (6), `ShipmentStatus` (8), `OrderStatus` (6), `OfferStatus` (5), `MessageType` (7), `PaymentHoldStatus` (5), `PromotionType` (2), `PromotionStatus` (4).

All nine are re-exported as **runtime values** from `@buttergolf/db` (`packages/db/src/index.ts`) so apps can use e.g. `OrderStatus.SHIPPED`.

### Order — money & escrow fields

`amountTotal`, `shippingCost`, `buyerProtectionFee`, `stripePlatformFee`, `stripeSellerPayout`; four unique Stripe IDs (`stripePaymentId`, `stripeCheckoutId`, `stripeTransferId`, `stripeChargeId`); dual shipper fields (EasyPost + ShipEngine legacy/current); label URLs (PNG/ZPL); lifecycle timestamps (`labelGeneratedAt`, `shippedAt`, `deliveredAt`); and the Vinted-style escrow trio: `paymentHoldStatus` (default `HELD`), `paymentHeldAt`/`paymentReleasedAt`/`autoReleaseAt`/`buyerConfirmedAt`. Dual address relations (`fromAddress`/`toAddress`). See [Payments & Escrow](payments.md) for the state machine.

## Integrity Rules

### Cascades — destructive and asymmetric

Deleting a **User** cascades: products, addresses, favourites, messages (sender), offers (both sides), ratings (all three FKs), promotions, conversations. Deleting a **Product** cascades: images, favourites, offers, conversations, promotions.

**Financial records are deliberately preserved**: `Order`'s FKs to buyer/seller/product/addresses specify **no cascade** (restrict) — so deleting a user who has orders **fails at the DB level**. Soft-delete (`User.isDeleted`) is the only supported path for active traders, and every public read path filters `user.isDeleted: false`.

`SetNull`: `Conversation.order` (order deletion unlinks but keeps the thread), `Message.offer`.

### Soft delete

Only on `User`. Products use `isSold`/`isDraft` flags instead — all public read paths filter `isSold: false, isDraft: false` (see `lib/listings.ts`).

### Idempotency (added by the `20260610120000_review_hardening_constraints_indexes` migration)

- `Product` unique `[userId, requestId]` — duplicate listing submissions are no-ops
- `Order` unique `stripeCheckoutId`, `stripeTransferId`, `stripeChargeId`
- `ProductPromotion` unique `stripePaymentId`

Plus hot-path composite indexes: `products(categoryId, isSold)`, `orders(buyerId, status)`, `orders(sellerId, status)`, `messages(conversationId, createdAt)`.

> The migration header warns the unique indexes fail if pre-existing rows violate them — data was reviewed on staging before production apply (merging to `main` deploys to production, so migration safety is assessed **before merge** and the migration is applied deliberately alongside the release).

### No optimistic locking

There is no `version` counter or conditional-update concurrency token anywhere. Concurrency control is achieved with atomic `updateMany` claims (e.g. the release cron claims an order by setting `HELD → RELEASED` in the WHERE clause) and Stripe idempotency keys (`release:${orderId}`, `double-sell-refund:${paymentIntent.id}`). Don't assume `updatedAt` is a concurrency token — it's a plain `@updatedAt` timestamp.

### Money is `Float`, not `Decimal`/`Int`

All money fields (`price`, `amountTotal`, fees, `offerAmount`) are `Float`. Known, deliberately deferred risk (DB-1 in `docs/CODEBASE_REVIEW.md`): the canonical pence-math in `@buttergolf/constants/checkout.ts` absorbs FP noise via `Math.round`, but any new money code should use the pence helpers rather than compounding float arithmetic.

## Client (`packages/db/src/index.ts`)

- Singleton `prisma` created in an IIFE, cached on `globalThis` outside production
- **React Native guard**: if running under RN, returns a `Proxy` stub that throws on model access — mobile must call backend APIs, never Prisma directly
- Type-only import of `PrismaClient` comes from the custom generated client (`../generated/client`); the same generated client is CommonJS-`require`d at runtime to keep Prisma out of RN bundles

## Scripts (`packages/db/package.json`)

`db:generate`, `db:migrate:dev`, `db:migrate:deploy`, `db:studio`, `db:seed` (tsx `prisma/seed.ts`), `postinstall` → `prisma generate`. `db:push` is defined but forbidden for schema changes (migration drift). Note: `db:fix-payment-hold` points at a script that was moved to `/scripts/fix-payment-hold-status.ts` — run it from there.

Seed: 3 demo users, 9 categories (from `@buttergolf/constants`), 33 brands, verified `ClubModel` rows from `prisma/fixtures/clubModels.json`, 8 sample products.

## Watch Out For

- **`packages/db/README.md` is stale** — it references a `Round` model (`prisma.round.create`) that does not exist in the schema. Don't document or copy it.
- User deletion with orders fails by design — soft-delete instead
- `ClubModel` drift: listings store free-text `model`, so the verified table can lag reality
- Denormalized `User.averageRating`/`ratingCount` must be maintained by app code on `SellerRating` writes
- 24 migrations exist (2025-10 → 2026-06); enum-value renames (e.g. `WARDROBE_SPOTLIGHT` → `PRO_SHOP_FEATURE`) were done via 3-phase temp-enum swaps — follow that pattern for enum changes
